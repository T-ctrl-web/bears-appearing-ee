## 审查清单

| # | 检查项 | 结果 | 备注 |
| --- | --- | --- | --- |
| 1 | 完整性 — 设计是否覆盖所有需求功能点 | **不通过** | App 模块接口未在 spec 中正式定义；密码强度提示方案要求"建议字母+数字组合"用词过弱，未设计强度校验逻辑与 UI；注册接口的账号枚举防护在设计层未覆盖 |
| 2 | 架构合理性 — 模块划分是否清晰、职责是否单一 | **通过** | 三层单向依赖 `kanban → auth → storage` 清晰，storage 唯一碰 localStorage，职责边界明确。但 spec 架构图只画了 3 个模块，实际代码有 4 个（app.js 未纳入架构图与接口定义） |
| 3 | 接口设计 — 接口是否合理、参数是否充分 | **不通过** | Storage 接口缺少批量更新方法，导致 moveTask 循环调用 updateTask 产生 N+1 读写问题；storage.js 内部 key 管理不一致（sessionStorage 用全 key，localStorage 用半 key）；App 接口完全未定义 |
| 4 | 可扩展性 — 后续迭代是否方便扩展 | **通过（有保留）** | 哈希函数独立成 `_hashPassword` 留 PBKDF2 升级口子，STATUS_LIST 数组可扩展，key 常量集中管理。但缺少数据版本号与迁移策略，任务模型无扩展字段设计 |
| 5 | 性能考量 — 是否有明显的性能瓶颈 | **不通过** | moveTask 拖拽排序时对列内每个任务单独调 Storage.updateTask，每次都全量读写 tasks 数组，N 个任务产生 N 次全量序列化反序列化；render() 每次操作都全量重建 DOM，无增量更新策略 |
| 6 | 安全基础 — 是否有常见安全漏洞 | **不通过** | 会话 token 设计声明"token 反查用户表"但实现未校验 token 有效性（设计未指定校验机制）；锁定路径直接返回不执行哈希，产生计时侧信道（安全设计未覆盖该路径）；注册接口暴露用户存在性 |
| 7 | 代码风格 — 与项目现有风格是否一致 | **通过** | IIFE 模式统一，JSDoc 注释完整，'use strict' 全覆盖，var 风格一致（兼容旧浏览器），命名规范统一。spec 示例用 async/await 但实现用 .then() 属合理兼容取舍 |
| 8 | 可维护性 — 是否易于理解和修改 | **通过（有保留）** | 模块分离清晰，注释解释"为什么"而非仅"是什么"。但魔法数字散落在 auth.js 中（MAX_FAIL/LOCK_DURATION/REMEMBER_DURATION）未抽取配置；_initDone 与 onsubmit 两种防重复绑定策略混用 |

## 问题列表

| # | 位置 | 问题 | 严重度 | 修复建议 |
| --- | --- | --- | --- | --- |
| 1 | spec.md 接口定义 → storage.js | **Storage 接口缺少批量更新方法，moveTask 产生 N+1 全量读写。** moveTask（kanban.js 第 178-185 行）对目标列每个任务循环调用 `Storage.updateTask(id, patch)`，而 updateTask 每次都执行 `this.get('tasks')`（全量反序列化）→ 修改一项 → `this.set('tasks', ...)`（全量序列化）。拖拽到含 50 个任务的列时，产生 50 次全量读写，性能瓶颈明显。设计层面的根因是 Storage 接口只设计了单条更新，缺少批量更新 API。 | 严重 | Storage 新增 `updateTasksBatch(updates)` 方法，接收 `[{id, patch}, ...]` 数组，一次读写完成全部更新。moveTask 改为先在内存中算好所有 patch 再一次性提交 |
| 2 | spec.md 安全设计 → auth.js 第 288-312 行 | **会话 token 设计声明"token 反查用户表"，但 checkSession 未校验 token 有效性。** spec.md 第 140 行明确写"校验时拿 token 反查用户表即可"，但 checkSession 实现仅检查 username 对应的用户是否存在，不校验 token 是否与登录时生成的一致。任何能写 sessionStorage 的代码可伪造会话。设计层面的问题是：spec 声明了 token 反查意图，但未设计具体的 token 校验机制（如用户表存 token 哈希、checkSession 比对），也未说明纯前端架构下如何缓解此局限。（对应蹦蹦测试报告 BUG-007） | 严重 | 设计层补充 token 校验方案：登录成功时将 token 哈希存入用户表（`sessionTokenHash`），checkSession 时用常量时间比对 token 哈希。纯前端无法完全防伪造，但应提高门槛并在 spec 中明确标注残余风险 |
| 3 | spec.md 安全设计 → auth.js 第 232-238 行 | **锁定路径不执行哈希，产生计时侧信道。** spec 安全设计要求"常量时间比对"防计时侧信道，但仅覆盖了密码比对路径。锁定用户 login() 直接 `Promise.resolve` 返回（第 235 行），不执行 SHA-256；未锁定用户即使密码错误也会执行哈希。攻击者可通过响应时间差异判断账户是否被锁定。设计层面的问题是安全设计只考虑了密码比对的计时均衡，未覆盖锁定检查路径的计时均衡。（对应 BUG-006） | 高 | spec 安全设计补充：所有拒绝路径（用户不存在、已锁定、密码错误）均执行等耗时哈希操作。锁定路径也调 `_hashPassword(password, user.salt)` 后再返回锁定提示 |
| 4 | spec.md 安全设计 → auth.js 第 157-165 行 | **密码强度校验设计要求过弱，"建议"非强制。** spec 第 128 行写"密码：长度 ≥ 6，建议字母+数字组合，给实时强度提示"。"建议"是弱约束，实现（validatePassword）只校验长度 6-20，未校验复杂度，未设计强度提示 UI。用户可用 `aaaaaa` 等弱密码注册。设计层面应将复杂度要求从"建议"提升为"必须"，并设计强度提示组件。（对应 BUG-008） | 高 | spec 修改密码要求为"必须包含字母和数字，长度 6-20"，validatePassword 增加复杂度正则校验，index.html 增加强度提示元素 |
| 5 | spec.md 安全设计 → auth.js 第 185-187 行 | **注册接口允许账号枚举，安全设计未覆盖。** spec 安全设计第 130 行仅要求"登录失败统一回'用户名或密码错误'，防账号枚举"，但未对注册接口提同等要求。注册时用户名已存在返回"用户名已被注册"，攻击者可通过尝试注册探测用户存在性，与登录防枚举设计不一致。（对应 BUG-012） | 高 | spec 安全设计补充注册接口的防枚举策略。方案一：注册成功后自动登录（减少暴露窗口）；方案二：统一返回"注册失败"不区分原因。在 spec 中明确取舍 |
| 6 | spec.md 接口定义 / 架构图 | **App 模块接口未在 spec 中正式定义。** spec 接口定义章节定义了 Storage、Auth、Kanban 三个模块的完整 API 签名，但 App 模块（app.js）仅在"页面结构设计"章节以代码片段形式出现，未纳入接口定义。实际代码中 app.js 是入口层，负责生命周期、视图切换、事件绑定，是第四个模块。架构图（第 19-35 行）也只画了三个模块，未包含 App。设计文档与实际实现不一致。 | 高 | spec 接口定义章节补充 App 模块的完整 API 定义（init/showView/bindEvents 等），架构图加入 App 作为入口层 |
| 7 | spec.md 数据结构 → kanban.js 第 269-273 行 | **任务 ID 生成方案使用 Math.random，碰撞风险高。** spec 第 195 行设计"task_ + 时间戳 + 4 位随机后缀"，实现用 `Math.random().toString(16).slice(2, 6)`，仅 65536 种可能。同一毫秒内批量创建任务（如性能测试 PERF-001 的 100 个任务循环）极易碰撞。设计层面应统一使用 `crypto.getRandomValues`，与盐值生成方式保持一致。（对应 BUG-002） | 高 | spec 修改 ID 生成方案为 `crypto.getRandomValues(new Uint8Array(4))` 转 hex（8 字节，42 亿种可能），与密码盐生成方式统一 |
| 8 | spec.md 接口定义 → auth.js 第 175-206 行 | **注册流程存在 TOCTOU 竞态设计缺陷。** spec 设计的注册流程为：findUser 检查 → 异步 _hashPassword → saveUser 保存。findUser 是同步检查，hashPassword 是异步操作，两者之间存在时间窗口。两个相同用户名注册请求可能同时通过 findUser 检查。saveUser 内部有二次检查会拒绝，但返回的错误信息是"注册失败，请重试"而非"用户名已被注册"。（对应 BUG-004） | 中 | spec 注册流程设计补充：saveUser 返回 false 时，register 应再次 findUser 检查是否因用户名重复，返回准确错误信息 |
| 9 | spec.md → kanban.js render() | **全量重渲染策略，无增量更新设计。** spec 第 309 行设计 render() 为"全量重渲染三列"，每次 addTask/deleteTask/moveTask/updateTaskTitle 都触发 render() 重建全部 DOM。任务量大时（200+ 任务），每次操作都重建数百个 DOM 节点。设计层面缺少增量更新策略（如只更新受影响的卡片）。 | 中 | 中期可设计增量更新：moveTask 只更新被移动卡片的 status/order 属性和受影响卡片的 order，不重建整个列表。或引入简单的 diff 策略 |
| 10 | spec.md 会话管理 → 全局 | **无跨标签页会话同步设计。** spec 会话管理设计未考虑同一用户在多个标签页打开的场景。标签页 A 登出后，标签页 B 的 sessionStorage 仍然有效（sessionStorage 是标签页隔离的，但 localStorage 记住我会话不是）。若使用"记住我"登录，标签页 A 登出清了 localStorage 会话，标签页 B 不会收到通知，刷新前仍显示已登录。 | 中 | spec 会话管理补充跨标签页同步方案：监听 `window.addEventListener('storage', ...)` 事件，当 localStorage 中的会话被清除时，同步切换到登录视图 |
| 11 | spec.md 数据结构 → 全局 | **无数据版本号与迁移策略设计。** spec 数据结构定义了用户、任务、会话的格式，但没有版本号字段。一旦后续迭代修改数据结构（如任务增加 priority 字段），现有 localStorage 中的旧格式数据无法被识别和迁移，可能导致解析异常。 | 中 | spec 数据结构增加全局版本字段 `sc:version`（当前值为 1），Storage 模块增加版本检查与迁移逻辑设计 |
| 12 | auth.js 第 23-26 行 | **安全参数魔法数字未集中管理。** MAX_FAIL=5、LOCK_DURATION=60000、REMEMBER_DURATION=7 天散落在 auth.js 顶部。spec 未设计统一的配置层，后续调整参数需要翻到具体模块。 | 低 | spec 新增"配置参数"章节，或在 storage.js 中定义 CONFIG 对象集中管理可调参数 |
| 13 | storage.js 第 226-242 行 | **key 管理方式不一致。** getSession() 中 sessionStorage 用 `KEY.SESSION`（已含 `sc:` 前缀的完整 key），localStorage 用 `this.get('session_remember')`（不含前缀，由 get 方法内部补前缀）。两种 key 传入方式混用，容易让维护者困惑。 | 低 | 统一 key 管理策略：要么全部用 KEY 常量（完整 key），要么全部用半 key（靠 get/set 补前缀），不要混用 |
| 14 | spec.md 防 XSS → index.html 第 7 行 | **CSP 允许 style-src 'unsafe-inline'，设计未评估 CSS 注入风险。** spec 第 120 行承认"样式留 'unsafe-inline' 是因为原生项目样式内联较多，CSS 注入危害低，务实取舍"。但 CSS 注入可通过属性选择器窃取数据（如 `input[value^="a"] { background: url(leak?a) }`），在含敏感输入的页面中风险不可忽视。设计层面应评估是否真正需要 'unsafe-inline'。 | 低 | 评估能否将内联样式全部迁到 style.css，去掉 'unsafe-inline'。若确需保留，在 spec 中补充 CSS 注入风险评估说明 |

## 审查结论

### 结论：驳回重跑

> 本鳄百事通，什么没见过！这设计...有问题，重做！

**驳回理由**：

本轮审查 8 项检查清单中 5 项不通过（完整性、接口设计、性能考量、安全基础，以及可维护性有保留），发现 14 个设计层面问题，其中：

- **严重问题 2 个**（#1 moveTask N+1 性能瓶颈、#2 会话 token 未校验）——一个影响核心交互性能，一个涉及安全核心设计声明与实现脱节，必须修复后方可通过。
- **高严重度问题 5 个**（#3 计时侧信道、#4 密码强度、#5 注册枚举、#6 App 接口未定义、#7 ID 碰撞）——涉及安全覆盖不全、接口文档不完整、数据唯一性风险，应在本轮一并修复。
- **中/低问题 7 个**——建议修复，不单独作为驳回理由，但严重度和高严重度问题修复时可顺带处理。

**修复优先级**（必须在本轮完成的）：

1. Storage 接口新增批量更新方法，消除 moveTask 的 N+1 读写（问题 #1）
2. checkSession 补充 token 校验机制设计，或明确标注残余风险并设计缓解方案（问题 #2）
3. 锁定路径补执行假哈希，消除计时侧信道（问题 #3）
4. 密码强度要求从"建议"改为"必须"，设计复杂度校验（问题 #4）
5. 注册接口防枚举策略纳入安全设计（问题 #5）
6. App 模块接口正式纳入 spec 接口定义章节（问题 #6）
7. 任务 ID 生成方案改用 crypto.getRandomValues（问题 #7）

**修复完成后提交第 2 轮审查。**

> 三模块分层是清爽的，密码加盐哈希方向是对的，防 XSS 的 textContent 策略也到位了——底子不差，但安全设计有漏洞、接口有缺口、性能有瓶颈。回去把这几条焊死再来见本鳄。 — 老鳄
