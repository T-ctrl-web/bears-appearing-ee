# 熊出没集团安全登录看板 — 测试用例报告

> 测试工程师：蹦蹦（松鼠，胆小但消息灵通）
> 口头禅："哎呀这个好吓人！但是我能找到Bug！"
> 测试对象：secure-kanban（安全登录看板）纯前端应用
> 测试范围：功能、输入校验、安全、边界、性能五大维度
> 代码版本：2026-08-19 熊二实现版

---

## 一、测试环境

| 项目 | 说明 |
| --- | --- |
| 浏览器 | Chrome 120+ / Firefox 121+ / Edge 120+ |
| 运行环境 | 本地文件协议或本地 HTTP 服务器（需支持 Web Crypto API） |
| 存储介质 | localStorage + sessionStorage |
| 前置数据 | 全新浏览器环境（无 sc: 前缀的 localStorage 数据） |

### 测试前准备

1. 打开浏览器开发者工具（F12），切到 Application > Storage，清除所有 `sc:` 前缀的 localStorage 和 sessionStorage 数据。
2. 刷新页面，确认显示登录视图。
3. 部分安全测试需要通过 Console 手动检查 localStorage 内容。

### BUG-001：登出未清除失败计数（P1）

- **文件**：`js/auth.js` 第 278-280 行
- **描述**：技术方案和 JSDoc 均声明"登出：清会话、清失败计数"，但 `logout()` 实现仅调用 `Storage.clearSession()`，未重置用户的 `failCount` 和 `lockUntil` 字段。
- **影响**：用户连续登录失败4次后登出，下次登录时若再失败1次即触发锁定（failCount 从4递增到5）。不符合"登出清零"的设计意图。
- **修复建议**：
```js
logout: function () {
  var user = this.currentUser();
  if (user) {
    Storage.updateUser(user, { failCount: 0, lockUntil: 0 });
  }
  Storage.clearSession();
}
```

### BUG-002：任务 ID 碰撞风险（P2）

- **文件**：`js/kanban.js` 第 269-273 行
- **描述**：`_genId()` 使用 `Math.random().toString(16).slice(2, 6)` 生成4位十六进制随机后缀，仅有 65536 种可能。在高频创建任务时（如性能测试批量创建100+任务）可能产生 ID 碰撞。
- **影响**：ID 碰撞后 `Storage.updateTask` 和 `Storage.deleteTask` 只操作第一条匹配记录，导致数据错乱。
- **修复建议**：改用 `crypto.getRandomValues` 生成随机后缀，与密码盐生成方式保持一致：
```js
_genId: function () {
  var ts = Date.now();
  var arr = new Uint8Array(4);
  crypto.getRandomValues(arr);
  var rand = Array.from(arr).map(function(b){ return b.toString(16).padStart(2,'0'); }).join('');
  return 'task_' + ts + '_' + rand;
}
```

### BUG-003：锁定后 lockUntil 残留未清理（P3）

- **文件**：`js/auth.js` 第 233-238 行、246-253 行
- **描述**：锁定到期后，`lockUntil` 字段仍保留旧的过期时间戳，直到下次登录成功或第5次失败才被覆盖。期间每次登录比对都会执行 `user.lockUntil > now` 的过期判断。
- **影响**：不影响功能正确性，但存储中残留过期数据，代码不够干净。
- **修复建议**：在锁定过期后的首次登录时，主动清除 `lockUntil`：
```js
if (user.lockUntil && user.lockUntil <= now) {
  Storage.updateUser(username, { lockUntil: 0 });
  user.lockUntil = 0;
}
```

### BUG-004：注册并发竞态条件（P2）

- **文件**：`js/auth.js` 第 175-206 行
- **描述**：`register()` 中先调 `Storage.findUser()` 检查用户名是否存在（同步），再异步调 `_hashPassword()` 生成哈希，最后调 `Storage.saveUser()` 保存。由于哈希是异步操作，两个相同用户名的注册请求可能同时通过 `findUser` 检查。
- **影响**：`saveUser` 内部有二次检查会拒绝第二条，但返回的错误信息是"注册失败，请重试"而非更友好的"用户名已被注册"。
- **修复建议**：在 `saveUser` 返回 false 时检查是否因用户名重复：
```js
var saved = Storage.saveUser(user);
if (!saved) {
  return { ok: false, msg: '用户名已被注册' };
}
```

### BUG-005：拖拽高亮残留（dragleave 未正确移除）（P3）

- **文件**：`js/kanban.js` 第 428-432 行
- **描述**：`dragleave` 事件处理器检查 `if (e.target === col)` 才移除高亮。当鼠标从列的子元素（如任务卡片）移出列边界时，`e.target` 是子元素而非 `col`，导致高亮不被移除。
- **影响**：拖拽离开列后可能残留蓝色高亮边框，视觉体验不佳。
- **修复建议**：使用 dragenter/dragleave 计数器或检查 `e.relatedTarget` 是否在列内：
```js
var dragCounter = 0;
col.addEventListener('dragenter', function(e) { e.preventDefault(); dragCounter++; col.classList.add('drag-over'); });
col.addEventListener('dragleave', function(e) { dragCounter--; if (dragCounter <= 0) { col.classList.remove('drag-over'); dragCounter = 0; } });
```

### BUG-006：锁定用户返回时间差可计时侧信道（P2）

- **文件**：`js/auth.js` 第 232-238 行
- **描述**：账户锁定时，`login()` 在哈希计算之前直接返回锁定提示（第 235 行 `Promise.resolve`）。未锁定用户即使用错密码也会执行 SHA-256 哈希（耗时操作）。攻击者可通过响应时间差异判断账户是否被锁定。
- **影响**：暴力破解时可探测哪些账户已锁定，辅助攻击策略调整。
- **修复建议**：锁定状态下也执行一次假哈希以消耗时间：
```js
if (user.lockUntil && user.lockUntil > now) {
  var remain = Math.ceil((user.lockUntil - now) / 1000);
  var self = this;
  return self._hashPassword(password, user.salt).then(function() {
    return { ok: false, msg: '登录失败次数过多，请 ' + remain + ' 秒后再试' };
  });
}
```

### BUG-007：会话 token 未做有效性校验（P1）

- **文件**：`js/auth.js` 第 288-312 行
- **描述**：`checkSession()` 仅校验 session 中的 `username` 对应的用户是否存在，不校验 `token` 是否与登录时生成的一致。任何能写入 sessionStorage 的代码均可伪造会话：只需写入 `{username: '存在的用户名', token: '任意值'}` 即可通过 `checkSession`。
- **影响**：若存在 XSS 漏洞（虽本项目已用 textContent 防护），攻击者可伪造会话冒充任意用户。纯前端架构无法完全解决此问题（无服务端 token 存储），但应在文档中明确标注此局限。
- **缓解建议**：在用户表中存储最近一次登录的 token 哈希，`checkSession` 时校验 token 匹配：
```js
// 登录成功时
Storage.updateUser(username, { sessionTokenHash: self._hashToken(session.token) });
// checkSession 时
var expectedHash = self._hashToken(session.token);
if (!self._timingSafeEqual(expectedHash, user.sessionTokenHash || '')) {
  Storage.clearSession();
  return null;
}
```
注：纯前端方案中 token 存 localStorage 仍可被读取，但增加了伪造门槛。

### BUG-008：密码强度校验缺失（P2）

- **文件**：`js/auth.js` 第 157-165 行
- **描述**：技术方案要求"密码 ≥ 6，建议字母+数字组合，给实时强度提示"。实现仅校验长度（6-20），未校验密码复杂度（是否包含字母+数字），未提供实时强度提示。
- **影响**：用户可使用 `aaaaaa` 等弱密码注册，密码安全性不足。
- **修复建议**：增加复杂度校验和强度提示 UI。

### BUG-009：密码 maxlength 限制过严（P3）

- **文件**：`index.html` 第 44 行
- **描述**：密码输入框 `maxlength="20"`，技术方案仅要求"密码 ≥ 6"未设上限。20 字符上限过于严格，现代安全实践鼓励使用长密码或密码短语。
- **影响**：用户无法使用超过20字符的密码。
- **修复建议**：移除或增大 maxlength（如 128），同步调整 `validatePassword` 的上限。

### BUG-010：查询选择器拼接用户可控值（P3）

- **文件**：`js/kanban.js` 第 77-78 行
- **描述**：`render()` 中使用 `'.col[data-status="' + task.status + '"] .task-list'` 拼接 CSS 选择器。虽然 `task.status` 通常为 `todo`/`doing`/`done`（由 `moveTask` 校验），但若 localStorage 被篡改注入非法 status 值，可能破坏选择器解析。
- **影响**：低风险，不影响安全性（不涉及 HTML 注入），但可能导致渲染异常。
- **修复建议**：增加 status 白名单校验后再拼选择器，或使用 `data-*` 属性匹配。

### BUG-011：用户名 autocomplete 值不规范（P3）

- **文件**：`index.html` 第 30 行
- **描述**：用户名输入框使用 `autocomplete="new-password"`，这是密码字段的 autocomplete 值。用户名字段应使用 `autocomplete="username"`。
- **影响**：部分浏览器密码管理器可能无法正确关联用户名与密码。
- **修复建议**：用户名输入框改为 `autocomplete="username"`（登录模式）或 `autocomplete="new-password"`（注册模式时动态切换）。

### BUG-012：注册接口可做账号枚举（P2）

- **文件**：`js/auth.js` 第 185-187 行
- **描述**：注册时若用户名已存在，返回"用户名已被注册"。攻击者可通过尝试注册来探测哪些用户名已注册（账号枚举）。
- **影响**：与登录的防枚举设计不一致，注册接口暴露用户存在性。
- **缓解建议**：纯前端无法完全防止（注册必须查重），但可在注册成功后自动登录而非要求二次登录，减少暴露窗口。或考虑注册不提示具体原因，统一返回"注册失败"。

### BUG-013：内联编辑 blur 与 Enter 双触发隐患（P3）

- **文件**：`js/kanban.js` 第 362-385 行
- **描述**：内联编辑中，按 Enter 触发 `save()`，随后 input 失去焦点触发 `blur` 事件也调用 `save()`。代码用 `done` 标志防止重复执行，逻辑正确。但 `save()` 调用 `updateTaskTitle` → `render()` 会销毁 input DOM，此时 `blur` 事件是否触发依赖浏览器实现。
- **影响**：目前 `done` 标志可正确防护，但属于脆弱实现。若未来重构去掉 `done` 标志，可能重复执行。
- **修复建议**：在 `save()` 和 `cancel()` 中先移除事件监听器再执行操作。
